# ExpressJS Framework Post Mortem

While TypeScript isn't my strongest suite within my toolbelt, I've come to appreciate the simplicity the ExpressJS provides. By this point, its becomes obvious that I prefer freedom in deciding how my project looks like rather than following an opinionated method. Just like Gin and FastAPI, ExpressJS is quite barebones. So file structures and conventions must be taken into consideration when planning an ExpressJS project. 

Throughout my experience job hunting, its quite often to find job postings that require proficiency in ExpressJS. Before doing this project, I always had this perception that ExpressJS is difficult to pick up and understand. Not to mention, out of all the JS backend framework out there, Express is probably the oldest that is still being used till today (until companies decide to migrate to Gin or some Rust framework because its 'faster', Lord knows what these people are thinking). But I stand corrected (after trying Gin and FastAPI), and I find ExpressJS pleasant to work with (better that trash ASP.NET Core, that's for sure).

In my first 4 hours of starting this project, I was struggling to set up the docker container because I was trying `pnpm` Docker image instead of the usual nodejs path. Thats it. So lesson learn, just use nodejs docker image to create a dockerized nodejs related project. Install pnpm via `Dockerfile` instead to save myself from the headache. Once I got this sorted out, it was pretty much smooth sailing from here. I admit, my entry for ExpressJS could've been designed better but this project is simply an exploration project, to experience all the backend framework used in the industry so I don't want to waste too much time over-optimizing and nitpicking every detail only to learn not much.

Then the usual 5 dummy controllers -> 5 dummy services -> connect the app to the db -> 5 proper endpoints and voila, thats it. But then I've come a realisation which I should've noticed since my Gin tour, these three frameworks do not have a standardized way of handling HTTP exceptions. Back in Gin, I did `http.Status..`, while in FastAPI I did `raise HTTPException`. So in ExpressJS, I decided to try and make my own middleware that handles HTTP exceptions. Well, at least that's what I thought, but as of writing this post mortem, I don't think I managed to write a proper middleware. 

Note to self: Learn how HTTP Exceptions work, how and where to catch it.

Apart from this slight divergence, not much is there to say regarding ExpressJS itself. I can see why many organizations and projects would choose ExpressJS for their backend application. However, just like other less to unopinionated frameworks, this requires some deep level understanding of system architecture to be able to take full advantage of this framework's full capabilities. Otherwise, you'll end up with deeply coupled, spaghetti of a codebase riddled with cruft (technical debt) and no one wants to work with it in the end. Trust me, you don't want to work with a codebase riddled with cruft. It's frustrating and agitating (combine it with stupid management who can't even spend a small amount of time to understand proper software development process and expect things to be shipped perfectly).

Conclusion: ExpressJS is pretty good.
